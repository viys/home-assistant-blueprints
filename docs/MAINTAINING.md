# Maintaining the manual

The site uses Astro and Starlight. User guides are ordinary Markdown in
`src/content/docs/`; the selection homepage is `index.mdx` and uses Starlight's
link cards. Standalone illustrations live in `public/diagrams/`.

## Preview and build

Use a Node.js version accepted by `package.json` (CI uses Node 24). From the
repository root:

```powershell
npm ci --prefix docs
npm run dev --prefix docs
```

Open `http://localhost:4321/home-assistant-blueprints/`. For the production build,
including the search index:

```powershell
npm run build --prefix docs
python tools/check_site.py docs/dist
npm run preview --prefix docs
```

Preview the production build at `http://localhost:4321/home-assistant-blueprints/`.
Starlight's search index is generated by the production build, not the dev server.

## Add or update a guide

Each blueprint has one guide and one SVG using its YAML filename stem. The guide's
front matter contains `blueprint: <yaml_filename_stem>`; the shared title component
creates stable import, raw YAML, source, and development links from that field.
Keep the title equal to `blueprint.name` and document integration differences.
Show the minimum HA Core version in each guide and the device overview. Keep
it consistent with the YAML's `blueprint.homeassistant.min_version`. Shared
pages should tell readers to check their chosen guide rather than list version
floors or model-specific exceptions. Device selectors with `model_id`
require at least Core `2025.4.0`; preserve the TRV-ZBL blueprint's higher
`2025.10.0` requirement. Keep version explanations on the website, not in the
README catalogue. Sources:
[Core 2025.3 selector schema](https://github.com/home-assistant/core/blob/2025.3.0/homeassistant/helpers/selector.py#L159)
and [Core 2025.4 selector schema](https://github.com/home-assistant/core/blob/2025.4.0/homeassistant/helpers/selector.py#L159).

The current version floor is based on metadata and source inspection; a real
HA import and device interaction at each minimum version have not been
validated here. Record any future manual validation with the Core version,
integration/handler or converter revision, firmware, and observed result.
Offline tests check the known selector version boundary and guide metadata
consistency; they are not a substitute for HA schema and hardware validation.

Use overview tables to compare source/target counts, integrations, and where
averaging happens. Keep parameter tables concise; put expiration rules and
other behavior in dedicated sections. Place synchronization triggers next to
configuration and make verification steps describe an observable device result.
Use Home Assistant's official `https://my.home-assistant.io/badges/blueprint_import.svg`
badge at `40px` high for **Import blueprint** on the website; keep the compact
README badges at their existing size. Preserve the
official artwork and the image's accessible label; do not add custom button
colors, padding, or an extra arrow. Stable raw YAML, source, and development
YAML belong under **Other download options**. Preserve a full-size diagram
link without repeating mobile scrolling instructions on every page.
Keep shared pages free of model-specific requirements and examples. Only the
homepage's **Find your device** section lists models; device details belong in
their overviews and blueprint guides.
Use `sidebar.label` for a shorter navigation label, and `sidebar.order` to order
guides within a device group.

Illustrations explain the user's outcome with example readings, rather than
repeating the configuration form. Keep a consistent white canvas, HA colors,
CJK-capable font stack, and accessible SVG `title` and `desc`. Vary the layout
with the behavior: fan out to multiple targets, converge for an HA average,
keep separate remote sources on separate paths, and show independent temperature
and humidity updates. Label device-side averaging separately from HA averaging,
and distinguish measured temperatures from target setpoints. Device drawings
and remote-input lists are schematic, not screenshots of physical displays.
Keep integration-specific source and target limits visible. Render every changed
SVG and check labels, arrow endpoints, and clipping at desktop and mobile widths.

Links in the manual are relative to the **published route**, with a trailing
slash, rather than the source Markdown file. From a blueprint guide, use
`../../../getting-started/` for the common guide and
`/home-assistant-blueprints/diagrams/<stem>.svg` for a public illustration.
Astro resolves relative Markdown images as source assets, so public image URLs
include the configured repository base path explicitly.

The `blueprint` field is validated by `src/content.config.ts`. Font files are
bundled through Fontsource packages; rendering does not require Google Fonts.
Keep presentation changes in `src/styles/custom.css` and preserve Starlight's
navigation, search, mobile menu, and table-of-contents behavior. The manual always
uses Light, regardless of system settings or previously saved theme preferences.
Keep the `LightTheme.astro` provider and empty `ThemeSelect.astro` override; do not
restore the Dark / Light / Auto selector. Customize colors under
`[data-theme='light']`.

At desktop widths of at least `72rem`, use a centered `94rem` shell with shared
outer margins for the header and both sidebars. The navigation is `22rem` and
the right-hand contents column is `15rem`; keep the article's `52rem` reading
width. Below that breakpoint, retain Starlight's tablet and mobile layout.

Match Home Assistant's color roles rather than using one blue everywhere:
`--ha-brand-blue` (`#18bcf2`) is the brand icon and selected-navigation accent,
`--ha-link-blue` (`#007fa8`) is the readable link color, and
`--ha-highlight-blue` (`#1abcf2`) is used for diagram arrows and focus outlines.
Set `--sl-color-text-accent` explicitly to `--ha-link-blue` so device cards,
device overview links, and guide links share the official text-link blue.
The import badge uses its official artwork colors. Keep the other tokens in
`src/styles/custom.css` and diagram colors synchronized. Sources:
[HA website colors](https://github.com/home-assistant/home-assistant.io/blob/current/sass/homeassistant/_variables.scss)
and [header button styles](https://github.com/home-assistant/home-assistant.io/blob/current/sass/homeassistant/base/_header.scss).

The favicon and title icon share `public/blueprint.svg`, using the
`mdi:palette-swatch` shape selected by
[HA's Blueprints navigation](https://github.com/home-assistant/frontend/blob/dev/src/panels/config/config-sections.ts).
Preserve its source and license notice in `public/LICENSE-MDI.txt`. The unused
social-icon separator is hidden because this manual has no theme selector.
The `SocialLinks.astro` override adds an accessible SONOFF official website link
(`https://sonoff.tech/`) beside the built-in GitHub icon, including in the
mobile menu. Its local `public/sonoff-favicon.png` comes from the official
[website favicon](https://sonoff.tech/cdn/shop/files/SONOFF-favicon.png?v=1747725092&width=96).
Preserve the icon's original colors and the link's accessible label.
Keep GitHub on the left and SONOFF on the right. Display the SONOFF favicon
with a circular crop at the same `1em` size as the GitHub icon.
Keep the GitHub icon black rather than inheriting the blue text-link color.

## Publish

Set **Settings > Pages > Build and deployment > Source** to **GitHub Actions**.
Pushes or manual runs on `master` and `dev` publish the same site; the most
recent successful deployment replaces its content. Pull requests build only.
Both branch publishing and tagged releases reuse `manual-build.yml` to check
the production site and upload its artifact. Allow `master`, `dev`, and tags
matching `v*` in the `github-pages` environment's deployment rules.

Stable version tags validate and fast-forward `master` using the built-in
GitHub token, then deploy the checked artifact explicitly. See
[Releasing](RELEASING.md) for the branch protections, tag commands, validation
steps, and failure handling. No separate development site is published.

If the repository is renamed or a custom domain is added, update `site` and
`base` in `astro.config.mjs`, the workflow's link-check base path, and README
website links together. All import buttons still point to the stable YAML in
`automation/sonoff/`; the manual does not duplicate blueprint definitions.
